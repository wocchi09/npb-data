# 牽制・ボークによる打席の取りこぼし修正

## 症状

特定の打席で、公式の球数（boxscoreの`pitches`）と収集済みの投球明細の合計球数が
食い違う。例: 2026-09-05 西武 vs ソフトバンク（`data/2026/09/05/2021039383.json`）の
隅田知一郎投手は、公式成績で100球のところ投球明細の合計は96球しか無かった。

原因を追うと、7回裏の今宮健太の打席（index=0720300）が「1塁けん制」でアウト2の
まま記録が止まっており、次の8回裏はアウト0・走者なしから始まっていた。つまり
今宮の打席の本当の結末（残りの投球・イニングを終わらせた本当の3人目のアウト）が
丸ごと収集できていなかった。

全733試合を走査すると、285試合（約39%）で同じパターンの半イニングが362件見つかり、
うち91件は走者が2〜3人乗ったまま次の回にリセットされる、見た目にも不自然な形に
なっていた。

## 原因

`scraper/main.py`の`collect_game()`は、打席ページのindexを

```
idx = f"{inning:02d}{tb}{order:02d}00"
```

で自分で組み立て、`order`（打者番号）を1ずつ進めるだけで全打席を辿っていた。
牽制やボークで打席が中断されると、サイト側では同じ打者の続きが別のindex
（連番の`order+1`ではない）に存在するとみられるが、この単純な連番方式では
そのindexを発見できず、「次のorderが無効＝イニング終了」と誤判定して
打ち切ってしまっていた。

なお`parser.py`にはページ内の`score?index=…`リンクを全て拾う
`extract_atbat_indexes()`という関数が存在していたが、`main.py`にimportされた
まま一度も呼ばれていなかった（未配線の関数）。

## 修正内容

### 今後の収集（`scraper/main.py`）

`collect_game()`で、取得した全ページ（起点ページ・各打席ページ）から
`extract_atbat_indexes()`で見つかったindexを`known_indexes`として蓄積するように
した。ある半イニングの最後の打席が、アウト3未満のまま「ボール」「見逃し」
「空振り」「◯塁けん制」「ボーク」等の“結論ではない”状態で止まっていたら
（`looks_interrupted_atbat()`で判定）、その半イニング宛でまだ取得していない
indexを`known_indexes`から探して追いかけて取得する。見つからない・結論が
付くまで繰り返す（無限ループ防止の安全弁つき）。巡回の最後にも、どこかで
見つかったが未取得のまま残っているindexを拾う最終セーフティネットがある。

牽制・ボークが無い通常の半イニングでは、ページ内リンクから新しいindexが
見つからないため、これまでと全く同じ挙動になる（`tests/test_scraper_main.py`の
回帰テストで確認）。

### 過去に収集済みの試合の復元（`scraper/backfill.py`）

`python scraper/backfill.py --what atbats`で、`find_interrupted_half_innings()`が
同じ基準で中断箇所を検出し、`repair_atbats()`が中断ページを取り直して続きを
追いかけ、既存の`atbats`に挿入する（`atbat_count`/`pitch_count`も更新）。
中断が見つからない試合は自動でスキップするため、既存の`stadium`/`boxscore`と
同じく何度実行しても安全（冪等）。GitHub Actionsの「Backfill Missing Data」を
`what: atbats`（または`stadium,boxscore,atbats`）で手動実行すると反映できる。

## 制約

この環境（サンドボックス）からは収集元サイト（baseball.yahoo.co.jp）への
外部通信がブロックされており、実際のページで修正の効果を確認できていない。
ロジックは`tests/test_scraper_main.py`・`tests/test_backfill.py`でモックした
HTML/index応答に対してのみ検証済み。次回のスケジュール収集、または
`--what atbats`のバックフィル実行時に、実データで復元されるか確認すること。
